# 产品与技术协作使用手册

这套能力用于把“产品想法”变成“可开发、可验证、可追踪的交付”。它把产品同学、Product Agent、技术同学、Technical Agent、开发任务和 UAT 放在同一条流程里。

## 1. 角色和边界

### 产品同学

- 在 Web 的“产品协作”页面创建需求。
- 与 Product Agent 多轮沟通，澄清用户问题、范围、流程、异常和验收标准。
- 可以查看当前项目的源码和文档分析结果。
- 只能编辑产品方案，不能修改项目源码、部署服务或提交代码。
- 确认产品方案后，将需求交给技术同学。
- 开发完成后负责填写验收意见并通过或退回。

### Product Agent

Product Agent 是 Taskboard 托管的持久化 Codex session/thread，不是另一个独立的业务系统。

- 工作目录指向所选项目的真实源码目录。
- 可以只读检查完整源码、`docs/blueprint.md`、`docs/blueprint/` 和现有文档。
- 不能直接写入源码、提交 Git、部署服务或伪造实现结果。
- 对话记录和文档版本由 Taskboard 保存。

### 技术同学

- 读取已确认的产品方案和项目源码。
- 与 Technical Agent 多轮讨论架构、接口、数据、权限、安全、测试、发布和回滚。
- 只能编辑技术方案和交付证据。
- 确认技术方案后，进入实现和测试阶段。

### Technical Agent

Technical Agent 是同一需求下独立持久化的 Codex session/thread：

- 复用项目真实工作目录，只读检查源码和文档。
- 不能直接修改源码、提交代码或声称已经完成开发。
- 必须将产品方案中的全部 `AC-*` 映射到技术验证方式。
- 必须明确功能验收后如何更新项目蓝图。

## 2. 前置准备

### 本地启动

```bash
npm install
npm run build
npm start
```

打开 `http://127.0.0.1:47823`。

开发前端时可以使用：

```bash
npm run dev
```

### 注册项目

项目必须绑定真实源码目录。可以在 UI 中注册，也可以使用 CLI：

```bash
npm run taskctl -- project create \
  --id skillhub \
  --name "SkillHub" \
  --workspace-path /Users/Admin/work/skillhub
```

`workspacePath` 是 Agent 只读分析和后续本地开发的依据。不要把临时目录、构建产物目录或不完整的源码副本注册为正式项目。

### 配置共享 Web 访问

公网或内网穿透场景必须启用认证。示例：

```bash
CODEX_TASKBOARD_PUBLIC_USERS='{
  "product":{"password":"CHANGE-ME","role":"product","name":"产品负责人"},
  "technical":{"password":"CHANGE-ME","role":"technical","name":"技术负责人"},
  "admin":{"password":"CHANGE-ME","role":"admin","name":"管理员"}
}' \
CODEX_TASKBOARD_HOST=127.0.0.1 \
npm start
```

密码只能通过安全渠道交给协作者，不要写入 Git、需求描述或日志。局域网无认证模式只适用于完全可信的网络。

## 3. 标准目录和文档

每个需求都会在项目源码中生成一个功能目录：

```text
docs/prds/<日期>-<功能slug>-<id8>/
├── feature.json   # 状态、负责人、哈希、交付证据和验收元数据
├── product.md     # 已确认产品方案
├── technical.md   # 已确认技术方案
└── uat.md         # UAT 前提、逐条验收结果和结论
```

项目当前能力蓝图位于：

```text
docs/blueprint.md
docs/blueprint/       # 可选的分域蓝图目录
```

蓝图记录“系统现在具备什么能力”；PRD 和技术方案记录“本次需求改变了什么”。功能验收通过前，蓝图必须真实更新，否则服务端会拒绝“验收通过”。

## 4. 产品阶段

1. 产品同学进入“产品协作”，点击“新建产品需求”。
2. 输入清晰的功能标题，不要把实现方案直接写进标题。
3. Product Agent 会先读取源码、蓝图和相关文档，再提出澄清问题。
4. 产品同学围绕以下内容多轮确认：
   - 要解决的用户问题和目标用户。
   - 现有 SkillHub 能力、入口和限制。
   - 目标与非目标。
   - 正常流程、异常流程和权限边界。
   - 功能需求、界面状态和兼容影响。
   - 可执行的验收标准。
5. Agent 生成产品方案后，产品同学可以“采用最近回复”，也可以手动修改 Markdown。
6. 点击“保存产品方案”后，Taskboard 写入 `product.md`。
7. 产品同学确认方案。确认后会创建开发任务，状态进入“技术接手”。

产品方案至少应包含以下二级标题：

```text
## 背景与问题
## 现有能力依据
## 与现有 SkillHub 的关系
## 目标与非目标
## 目标用户与入口
## 用户流程
## 功能需求
## 界面与状态
## 兼容影响
## 验收标准
## 待确认事项
```

未决问题必须写在“待确认事项”，不能用模糊表述把未决范围伪装成已确认需求。

## 5. 技术阶段

1. 技术同学打开产品协作中的同一需求。
2. 技术 Agent 读取已确认产品方案、当前源码和蓝图。
3. 技术同学继续追问实现边界、依赖、风险和验证方法。
4. Agent 输出技术方案，技术同学检查并保存。
5. 技术方案确认后，开发任务进入“开发就绪”。此时才开始编码。

技术方案至少应包含以下二级标题：

```text
## 产品规格基线
## 当前实现证据
## 技术方向
## 影响设计
## 实施计划
## 验证映射
## 蓝图更新范围
## 部署与回滚
## 风险与技术决策
```

“验证映射”必须覆盖产品方案中的每一个 `AC-*`。技术方案不能只写“补测试”，要说明测试层级、目标文件或运行方式和通过条件。

## 6. 开发和交付

开发必须依据已确认版本实施。产品或技术范围发生变化时，回到协作会话更新文档，不要只在代码评审里口头改变范围。

技术同学在交付区填写：

- 实现 PR 地址。
- 共享测试环境地址。
- 部署工作流地址。
- 不可变构建标签或镜像标签。
- 部署包含的 PR 编号。
- 实现范围、测试结果和已知风险。

点击“提交产品验收”后，Taskboard 会将开发任务置为 `in_review`，并生成 `uat.md`。

交付证据应指向真实资源。示例地址只能用于本地流程测试，不能作为正式验收依据。

## 7. UAT 和蓝图门禁

产品同学在验收页逐条检查：

1. 产品方案和技术方案版本是否正确。
2. 实现 PR 是否包含在当前范围内。
3. 测试地址是否可访问。
4. 工作流、不可变标签和 PR 编号是否能追溯。
5. 所有验收标准是否有实际证据。
6. `docs/blueprint.md` 或 `docs/blueprint/` 是否已记录新能力。

验收成功的必要条件：

- 当前交付任务处于 `in_review`。
- 产品、技术文档和 UAT 产物完整。
- 当前完整蓝图路径集合可计算并能读取。
- 当前蓝图哈希与需求创建时的基线哈希不同。
- `feature.json` 记录更新后的蓝图路径、哈希和时间。

如果蓝图未更新，服务端会返回“请先更新项目功能蓝图”，不会把需求标记为完成。退回修改会把任务恢复到开发中，并保留验收意见。

## 8. 推荐协作方式

### 产品同学的提问模板

```text
请先基于当前项目源码、docs/blueprint.md 和现有文档说明：
1. 当前已有能力和可复用入口；
2. 本需求会受到哪些真实限制；
3. 还缺哪些产品决策。
暂时不要给技术实现方案。
```

### 技术同学的提问模板

```text
请基于已确认产品方案和当前源码：
1. 列出涉及的模块和接口；
2. 逐条映射全部 AC-*；
3. 说明测试、部署、回滚和蓝图更新范围；
4. 标出仍需产品确认的技术风险。
不要修改源码，先输出技术方案。
```

### 需求变更规则

- 变更用户目标、范围或验收标准：回到产品阶段，生成新产品文档版本。
- 只变更实现方式：回到技术阶段，生成新技术文档版本。
- 变更已上线能力：更新蓝图，并在 PRD 的兼容影响或技术方案的蓝图范围中留下记录。
- 不要在多个需求目录复制同一份“当前蓝图”。蓝图只有一个当前真相。

## 9. 权限和安全

- 产品角色：可创建产品需求、发送产品 Agent 消息、保存产品文档和确认产品方案；不能写技术方案或普通开发任务。
- 技术角色：可读取产品文档、发送技术 Agent 消息、保存技术文档、确认技术方案、更新开发任务和提交交付；不能改产品文档。
- 管理员：拥有项目和任务管理权限。
- Agent 的“可读源码”不等于“可写源码”。源码修改必须发生在开发任务绑定的正常开发会话中。
- 公网共享必须使用认证、HTTPS 或可信内网边界；不要把 Basic 密码放到 URL。
- 不要把 token、Cookie、内部服务地址、堆栈或本机终端日志写入产品文档。

## 10. 故障排查

### 看不到产品协作

确认当前项目已选中，并检查 `/api/meta` 返回 `productCollaboration: true`。

### Agent 无法启动

确认项目的 `workspacePath` 是存在的目录，且 Codex 可执行文件和项目依赖已安装。后端会拒绝没有可用工作区的非本地协作会话。

### 技术同学无法发送消息

检查登录用户的角色是否为 `technical` 或 `admin`，并确认需求已经进入“技术接手”。产品角色不能调用技术写接口。

### 无法提交产品验收

按顺序检查：

1. 技术任务是否处于 `in_review`。
2. PR、测试地址、工作流、不可变标签和 PR 编号是否完整。
3. `docs/blueprint.md` 或 `docs/blueprint/` 是否发生真实内容变化。
4. 运行 SkillHub 的交付物校验器。

### 实时页面没有更新

刷新页面。Taskboard 的实时事件是刷新提示，重新连接后会执行完整快照刷新；不要把浏览器当前旧页面当作数据库状态。

## 11. 本地验证清单

在提交代码前运行：

```bash
npm run typecheck
npm run test:components
npm test
npm run build
git diff --check
```

SkillHub 功能产物校验：

```bash
python3 /Users/Admin/work/skillhub/.agents/skills/deliver-feature/scripts/validate_feature_docs.py --strict \
  /absolute/path/to/skillhub/docs/prds/<feature-directory>
```

浏览器验收至少覆盖：

- 产品角色创建需求、连续发送消息、保存并确认产品方案。
- 技术角色读取同一需求、发送消息、保存并确认技术方案。
- 技术角色填写完整交付证据并提交验收。
- 蓝图未更新时验收被阻止。
- 蓝图更新后验收成功，需求和开发任务均完成。
- 桌面和窄屏布局无横向溢出，输入框、按钮和文档区可操作。

## 12. 日常结束标准

一个需求只有同时满足以下条件才算完成：

- 产品方案已确认并归档。
- 技术方案已确认并归档。
- 开发任务有可追溯的 PR 和测试证据。
- UAT 文档逐条记录结果。
- 项目蓝图已更新并记录新哈希。
- 产品负责人已验收通过。
- Git、测试、构建和运行状态均已检查。
